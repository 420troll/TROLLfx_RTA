# V0.2 measurement engine

## Analysis design

Capture remains the v0.1.2 ALSA path: `hw:U18dB,0`, stereo packed `S24_3LE`, 48 kHz, `snd_pcm_prepare()` followed by explicit `snd_pcm_start()`, then `snd_pcm_readi()`. Channel 0 remains the analyzed channel. This process does not configure Force playback or ALSA routing.

Each analysis frame contains 32,768 samples (682.7 ms). A Hann window reduces leakage. PFFFT computes the real transform with reusable aligned buffers and its ARM NEON float backend. Spectral power is scaled by the FFT length and the window's sum of squared coefficients; positive-frequency bins are doubled except DC/Nyquist, then integrated as power over exact 1/3-octave edges. Fractional edge-bin overlap is included. This produces RMS power per band rather than the old mean of FFT magnitudes. Hop size is 4,096 samples (85.3 ms), so frames overlap by 87.5% and the latest frame is about 0.68 s long.

The 31 band centers use the established nominal sequence 20 Hz–20 kHz, with edge frequencies at center ×/÷ 2^(1/6). A 1 kHz tone therefore lands around the 1 kHz band instead of creating a large response in unrelated bands. The 16-band view combines adjacent band powers in the browser. The API supports configurable power averaging over 1, 2, 4, 8, or 16 analysis frames (default 1); this affects the spectrum bars only. Display gain, floor, smoothing, attack/fall, and peak hold are browser-only. SPL calculations remain independent of these display controls.

The longer FFT improves low-frequency bin spacing from 5.86 Hz to 1.46 Hz. IEC 61260 fractional-octave filter banks may better represent specified filter shapes and rejection, but a standards-verified filter design and measured conformance remain future work. The current FFT bands are energy measurements with standard band edges; this is not a claim of IEC filter compliance. A-weighted and Z-weighted SPL fields are available in the API when measured input sensitivity is supplied. This remains provisional for the Force/UMIK chain until verified with an acoustic calibrator.

## Microphone calibration

The individual `7033298.txt` and `7033298_90deg.txt` files are bundled under `calibration/`; each has 615 frequency/response points and `Sens Factor = 2.7673 dB`. The app loads them by default and allows overrides with `--cal-0 PATH` and `--cal-90 PATH`; `--orientation 0|90` selects the active curve. Log-frequency interpolation applies the response correction in FFT bins before band, Z, and A power integration. Tests parse both files, preserve the sensitivity metadata, verify the orientation curves differ, and cover sensitivity-to-SPL arithmetic.

The sensitivity factor is retained and reported, but is not treated as a direct dBFS-at-94-dB-SPL value for this Force capture path. REW documents that Sens Factor represents the expected input dBFS at 94 dB SPL when the mic input volume is maximum and that it can only be used when the device input-gain relationship is known ([REW calibration file help](https://www.roomeqwizard.com/help/help_en-GB/html/calfiles.html)). The Force ALSA/USB capture gain relationship has not been verified here. Until a measured anchor is supplied with `--sensitivity-dbfs-at-94 DBFS`, the API reports `spl_a` and `spl_z` as null and marks them provisional. Raw broadband dBFS and response-corrected Z/A dBFS remain available.

To verify sensitivity, apply a traceable 94 dB SPL, 1 kHz acoustic calibrator to the UMIK-1, capture the PCM stream with the Force's actual ALSA path and gain, and record channel RMS dBFS. The resulting measured dBFS at 94 dB SPL anchors `SPL = 94 + corrected dBFS - sensitivity_dBFS_at_94`. Confirm the same mapping after any USB path or gain change. The miniDSP SPLMeter instructions likewise say its correction-file sensitivity is read to set the SPL calibration offset ([miniDSP SPLMeter guide](https://www.minidsp.com/applications/acoustic-measurements/umik-1-splmeter)); this project still requires confirmation against the Force capture path.

## Source evaluation and licensing

| Project | License / implementation | Relevance |
|---|---|---|

The FFT power math is sound, although bands sum whole FFT bins rather than fractional edge bins and are not IEC filter-bank responses. Good reference; no source copied. |

The license is retained alongside the source. ARM runtime performance remains unmeasured. |
| [ninoblumer/python-soundlevelmeter](https://github.com/ninoblumer/python-soundlevelmeter) | GPL-3.0; time-domain Butterworth SOS octave filters generated through `phonometry`, with NumPy/SciPy and Numba processing. The project includes IEC 61260 Class 1 and IEC 61672 conformance tests. | Strong reference for filter-bank and weighting behavior. `phonometry`, Python ≥3.13, NumPy, SciPy, and Numba are unsuitable for this small C/ARM process; GPL code is not copied. |

The in-tree band, weighting, calibration, and SPL code is original. PFFFT is the only bundled third-party implementation; its license text is included at `src/third_party/pffft/LICENSE.txt`, and its copyright/license notice is retained in each upstream source file. The project-wide license remains to be selected by maintainers.

## Verification limits

`scripts/run-tests.sh` runs deterministic synthetic-signal checks and prints host timing. On this x86-64 host representative 100-frame runs measured V0.1.2 at 0.45–0.55 ms/frame and V0.2 with PFFFT at 0.83–1.1 ms/frame (about 1.5–2.2× per frame for 4× the sample count). The FFT-only PFFFT timing was 0.099 ms for 32,768 points. CPU frequency and host load change these timings. These are host timings, not an ARM CPU or latency claim. `scripts/build-armv7.sh` cross-compiles an ARMv7 hard-float executable into `dist/trollfx-rta-v02-armv7`. This environment has no Force or UMIK attached, so CPU use during Force playback, ALSA capture stability, USB sensitivity, and measured SPL calibration are not claimed.
